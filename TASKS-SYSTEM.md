# Система задач «Прогноз» — как работает сейчас

> Документ для проектного менеджера. Описывает **типы задач**, **механики авто-постановки**
> и — с особым акцентом — **воронки, особенно месячные**, как источник задач.
> Всё по реальному коду (файл:строка, пути RTDB, расписания кронов) на 2026-07-28.
> Бэкенд: `prognoz-functions/functions`. Фронт: `prognoz-dashboard`.

---

## 0. Как задача попадает к человеку (общий поток)

```
n8n → архив (bL/sL/commFact)                     Цель партнёра
        │                                              │
        ▼ nightlySnapshot (02:00 UTC)                  ▼ calculatePlan → нормы месяца
 /snapshots/{code}/{date}                        /plans/{code}/months[ym].norms
   · funnels (факт этапов)                            │
   · ir_total_month, ir_v2_month  ◄──────────────────┘  (факт месяца vs норма месяца = ИР)
        │
        ├── runScenariosDaily (06:00)   ─┐
        ├── genCoachTasksWeekly (пн 05:00)├─→  /tasks/{id}  ──→ фронт (таб «Задачи и календарь»)
        └── escalateNRiskDaily (04:30)   ─┘        ▲
                                     ручное создание (createTask из UI)
```

Задачи создаются **двумя путями**: вручную (партнёр/руководитель) и **тремя авто-движками**
(сценарии, задачи-тренера, эскалация риска). Все авто-движки читают ночные снапшоты и план.

## 1. Модель данных `/tasks/{id}`

id: `task_<pushKey>` (боевые) или `task_<seed>_<code>_<idx>` (тестовый сид). Поля
(`tasks.js:runCreateTask` 121-132):

| Поле | Значения | Смысл |
|---|---|---|
| `title` | строка 3–200 | Заголовок |
| `description` | строка ≤2000 / null | Детали |
| `assignee_code` | код | Исполнитель (по нему фронт подписывается) |
| `assignee_role` | realtor / mop / rop / aup | Роль исполнителя |
| `author_code` | uid (в сиде `mop:{id}` / `system:seed`) | Кто создал |
| `author_kind` | self / manager / **scenario** / ai_coach / mop / system | Тип автора |
| `author_label` | «Вы» / имя / **«ИИ-система»** | Подпись автора в UI |
| `priority` | critical / important / normal | Приоритет |
| `type` | client / base / team / free (`TASK_TYPES` `tasks.js:73`) | Тип (см. §2) |
| `due_at` | ms / null | Дедлайн-таймстамп |
| `due_date` | YYYY-MM-DD / null | Дата дедлайна |
| `status` | **active / done / skipped / expired** | Статус (финальные: done/skipped/expired) |
| `progress_done` / `progress_total` | int | Прогресс составной задачи |
| `created_at` / `done_at` / `expired_at` | ms | Времена |
| `related_client_id` / `related_user_id` / `related_scenario_id` | код / null | Связи (сценарий, клиент, пользователь) |
| `ui_group` | today / week / later | Группировка в UI по сроку |
| `calendar_synced` / `calendar_event_id` | bool / id | Синхронизация с Google Calendar |

Доп. поля от календаря/сида (не пишутся callable, читаются фронтом): `duration_min`,
`span`, `source` (моя задача/срочное/отклонение/план), `horizon`, `coach_bit`, `lever`,
`tool`, `seed_type`, `seed_funnel_stage`, `seed_segment`, `visible_to_mop`.

## 2. Типы задач — ДВЕ параллельные системы

**A. Боевые (callable `TASK_TYPES`, `tasks.js:73`):** `client` · `base` · `team` · `free` (дефолт `free`).
UI создания: партнёр — 🎯 free / 👤 client / 📋 base; старший партнёр — 👥 team / 🎯 free.

**B. Тестовый сид (`seedClients.js`):** `client` / `skill` / `manager` — **другой набор**, для демо-данных группы Колмогорова.
- 👤 **client** — по клиенту (заголовок зависит от этапа: hot/deposit/work/flow/cooling).
- 🎓 **skill** — по профилю партнёра (скрипты/вебинары/онбординг).
- 👔 **manager** — «от старшего партнёра».

Отображение иконок на фронте (`calendar.js:typeIcon` 427-432): 📅 событие, 👤 своя, 👔 менеджер, иначе 🤖 (ИИ).

> ⚠️ **Для ПМ:** типы/статусы/приоритеты сида (`skill`, `manager`, `open`, `high`) **не совпадают**
> с боевым набором callable. Это две несогласованные системы — стоит унифицировать.

## 3. Базовые функции задач (`tasks.js`, регион europe-west1)

| Функция | Тип | Что делает |
|---|---|---|
| `createTask` | onCall | Создаёт задачу себе/подчинённому. Проверки: права `isOverOrSelf` (38-44), антидубль 24ч по (assignee+author+title). Достраивает `due_at↔due_date`, `ui_group`, `author_label`. Шлёт `task_assigned` исполнителю |
| `updateTaskStatus` | onCall | active → `done`\|`skipped`. Права: done — исполнитель/вышестоящий, skipped — исполнитель/автор. Уведомляет автора |
| `updateTaskProgress` | onCall | `progress_done`; при достижении `progress_total` — автозакрытие в done |
| `expireTasks` | onSchedule `0 * * * *` (ежечасно) | active с `due_at < now` → `expired`, уведомление `task_overdue` (critical, звук call) |
| `markNotificationsRead` | onCall | Помечает уведомления прочитанными, пересчитывает `/notifications/{code}/meta` |
| `backfillTaskAuthors` | onCall (admin/aup) | Миграция: проставляет `author_label` |

Жизненный цикл: `active → done | skipped | expired`. Удаления задач в UI нет (только эти статусы;
полное удаление — лишь в админ-очистках сида).

## 4. Расписание кронов (суточно-недельная цепочка, UTC)

Порядок важен: снапшоты первыми, движки читают их результат. Даты внутри движков — `Asia/Yekaterinburg`.

| UTC | Функция | Файл:строка | Роль |
|---|---|---|---|
| 02:00 ежедн. | `nightlySnapshot` | nightlySnapshot.js:210 | Пишет `/snapshots` — факт воронки, `ir_total_month`, `ir_v2_month` |
| 04:30 пн | `runCoach` | runCoach.js:89 | 6-битная диагностика → `/coach/{code}/current` |
| 04:30 ежедн. | `escalateNRiskDaily` | escalateNRisk.js:261 | Эскалация Н1–Н4 |
| 05:00 пн | `genCoachTasksWeekly` | genCoachTasks.js:260 | Задачи-отклонения из coach-битов |
| 06:00 ежедн. | `runScenariosDaily` | runScenarios.js:257 | 4 сценария авто-задач |

> ⚠️ Комментарий в `escalateNRisk.js:8` говорит «06:00 UTC» — устарел; фактически `'30 4 * * *'` (04:30).

## 5. Движок сценариев — `runScenarios.js` (06:00, только `role=realtor`)

Все задачи помечаются `author_kind:'scenario'`, `author_label:'ИИ-система'`, `related_scenario_id`.
Антидубль — `scenarioDup`. Если сработал `no_deals_30d` — остальные сценарии для партнёра пропускаются (не плодим 3 задачи, 206-209).

| Сценарий | Условие (порог) | Данные | Создаёт задачу | Кому | Антидубль |
|---|---|---|---|---|---|
| **no_activity_2w** | заходил (login ≤14д), но `tasks_done_14d == 0`; не новичок (стаж >1) | активность (не воронка) | «Разобрать с {имя} — 2 недели без прогресса», critical, +5 раб.дней | **МОПу** + звонок-уведомление | 7 дней |
| **ir_dropped_2w** | `ir_total_month` упал ≥20 пп за 14 дней (было ≥50, стало <50) | месячный ИР (снапшот) | «{имя} — резкое падение ИР», important, type team, +2 дня | **МОПу** | 14 дней |
| **objects_below_norm** | объекты < 50% нормы месяца **во всех** снапшотах today/d7/d14 (норма ≥10) | **месячная норма** `plan.months.norms.seller.all.objects` vs `snapshot.funnels.seller.all.objects` | «Объекты в работе ниже нормы зоны», normal, type base, +7 дней | **партнёру** | 14 дней |
| **no_deals_30d** | сделок 0 и сегодня, и 30 дней назад; не новичок (стаж ≥2); без истории d30 — не триггерит | `funnels.buyer.all.deals + seller.all.deals` | «30 дней без сделок» партнёру (+5д) **и** «{имя} — 30 дней без сделок» МОПу (+3д, звонок) | партнёру **и** МОПу | 30 дней |

Управление: флаги `/scenarios/items/{id}/is_active`, счётчики `triggered_count_*`. Ручной запуск —
`runScenariosDailyAdmin`. Откат ложных — `cleanupScenarioTasksAdmin`.

## 6. Движок задач-тренера — `genCoachTasks.js` (пн 05:00)

Из 6-битной диагностики `/coach/{code}/current` (ветки buyer/seller). Для каждого бита со
значением **0 (слабо)** → задача **самому риелтору** (important, type free, `related_scenario_id:"coach_bit:{bit}"`,
поля `lever`, `coach_bit`, `tool`, source «отклонение»). Бит вернулся в **1** → задача авто-закрывается.
Смена `period_id` (новый месяц) → все coach-задачи старого месяца закрываются.

**Этап воронки → задача (таблица `COACH_BITS`):**

| Сторона | Бит | Этап | Задача |
|---|---|---|---|
| Покупатель | k_sufficiency_flow | Поток | Усилить лидогенерацию |
| Покупатель | k_sufficiency_hot | Горячие | Квалифицировать в горячие (скрипт) |
| Покупатель | k_sufficiency_deals | Сделки | Дожать задатки до сделки |
| Покупатель | p_conversion_to_hot / to_deals | Конверсии | Проработать скрипт / разобрать застрявшие |
| Продавец | k_sufficiency_objects | Объекты | Набрать объекты в работу |
| Продавец | k_sufficiency_hot_objects | Горячие объекты | Двигать к показам, статусы |
| Продавец | k_sufficiency_deals_objects | Сделки | Дожать задатки по объектам |
| Продавец | p_conversion_* / k_distribution_* | Конверсии / распределение | Разобрать причины / расширить сегменты |

> 🔑 **Ключевое отличие:** coach-биты считаются **не от месячной нормы**, а от **12-месячной нормы ЗОНЫ**
> партнёра (`data_division`, порог `факт ≥ 0.5 × норма зоны за 12 мес`). Это диагностика «как партнёр
> выглядит на фоне зоны за год», а не недобор конкретного месяца. См. §8.

## 7. Эскалация риска Н1–Н4 — `escalateNRisk.js` (04:30)

Стрик «плохих недель» считает `lib/riskStreak.js`. **Плохая неделя** = накопительный %
выполнения **месячного** плана ниже цели к неделе: `target(weekN) = weekN×25%` (25/50/75/100),
`threshold = target × tolerance` (default 0.90) → пороги 22.5/45/67.5/90%. Источник —
`/snapshots/{code}/{граница}/ir_v2_month/ir_total`. Границы недель: дни 7/14/21/конец месяца.
«Сегодня в плане» обнуляет стрик. Недели до `plan.created_at` не учитываются (смена цели = чистый лист).

| Уровень | Стрик | Задача | Кому | Срок |
|---|---|---|---|---|
| **Н1** | 1 | — (только счётчик и бейдж, задачи нет) | — | — |
| **Н2** | 2 | «Разобрать с {имя} — 2 недели ниже нормы», important | МОПу | +3 раб.дня |
| **Н3** | 3 | «{имя} — 3 недели в риске, нужен план выхода», critical | МОПу | +2 раб.дня |
| **Н4** | ≥4 | «🔴 {имя} — 4+ недели, эскалация РОПу», critical + звонок | МОПу **и уведомление РОПу** | +1 раб.день |

История — `/risk_history/{code}/{date}` (level norm/Н1…Н4). Антидубль 10 дней по (mopCode+partner+уровень).
Гард: пропуск неактивных, Группы 0, стажа <1 мес.

> ⚠️ Legacy-порог `/config/risk/week_floor` **больше не используется** — актуальный конфиг
> `/config/risk/week_tolerance` (default 0.90).

## 8. 🎯 ВОРОНКИ, ОСОБЕННО МЕСЯЧНЫЕ (ядро — источник задач)

### 8.1. Из чего складывается месячная воронка

Факт месяца — `lib/funnels.js` (`buildFunnelMonth`); норма месяца — `calculatePlan.js`/`lib/plan.js`
(a8v6); тип метрики этапа — `lib/ir.js` (`STAGE_KIND`). `all` этапа = **сумма сегментов**
(new/sec/out/com/gar). Вал (revenue) — из **реальных комиссий** `commFact`, а не сделки×чек.

| Сторона | Этап | ФАКТ (поле архива) | Тип метрики (STAGE_KIND) | НОРМА месяца | Как считается % (progress_pct) |
|---|---|---|---|---|---|
| Покупатель | **Поток** | `bL.{seg}.flowCur` | `cur` (накопит. с 1-го) | `norms.buyer.{seg}.flow` | факт / (план × прошло_дней/всего), cap 100% |
| Покупатель | **Горячие** | `bL.{seg}.hotAct` (темп 2 мес) | `snapshot` (остаток) | `norms.buyer.{seg}.hot` | факт / полный план |
| Покупатель | **Задатки** | `bL.{seg}.depCur` | `snapshot` | `norms.buyer.{seg}.deposits` (max с deals) | факт / полный план |
| Покупатель | **Вал** | `commFact.b*` (+прогноз) | `cur` | `target_revenue_buyer` | факт / (план × дни) |
| Продавец | **Объекты** | `sL.{seg}.actONCur` (остаток) | `snapshot` | `norms.seller.{seg}.objects` | факт / полный план |
| Продавец | **Горячие** | `sL.{seg}.hotONCur` (остаток) | `snapshot` | `norms.seller.{seg}.hot` | факт / полный план |
| Продавец | **Задатки** | `sL.{seg}.depCur` | `snapshot` | `norms.seller.{seg}.deposits` (max с deals) | факт / полный план |
| Продавец | **Вал** | `commFact.s*` (+прогноз) | `cur` | `target_revenue_seller` | факт / (план × дни) |

- **`cur`** (поток, вал): месячный факт сравнивается с планом к дате (× прошло_дней/всего) — процент растёт по ходу месяца.
- **`snapshot`** (горячие, задатки, объекты): это **остаток в работе на дату**, знаменатель — **полный план** (не пропорция дней).
- **Норма месяца (a8v6):** дельта `(зона_B − факт_A)×коэф + A`, разложенная по 6-месячной рампе (`plan.months[ym].norms`). Покупатель ×1. Задатки ≥ сделок.
- **Трёхчастность на фронте** (`getDashboard.buildFunnelBlock`): `факт / прогноз / план`; для денег есть прогноз-остаток к концу месяца, для не-денег — только факт/план. Статусы: green ≥70%, yellow ≥40%, red.

### 8.2. Месячная воронка → ИР → эскалация (модель ir_v2)

`ir_v2_month.ir_total = 0.25·C1 + 0.25·C2 + 0.25·C3 + 0.25·C4`, где компоненты — **факт/норма этапа**
месячной воронки: **C1** поток+объекты, **C2** горячие (остаток), **C3** задатки (остаток), **C4** вал.
Недобор **любого** этапа месячной воронки роняет `ir_v2_month.ir_total` → через `riskStreak` → **Н2/Н3/Н4** (§7).

### 8.3. Итог: какой недобор воронки → какая задача

| Недобор (что именно просело) | Сравнивается с | Движок → задача |
|---|---|---|
| **Объекты продавца** < 50% нормы **месяца** 2 недели | `plan.months.norms.seller.all.objects` | `objects_below_norm` → партнёру |
| **Сделки** (buyer+seller) = 0 за 30 дней | `snapshot.funnels.*.all.deals` | `no_deals_30d` → партнёру + МОПу |
| **Месячный ИР** упал ≥20 пп за 2 недели | `snapshot.ir_total_month` | `ir_dropped_2w` → МОПу |
| **Накопит. % месячного плана** (ir_v2, любой этап C1–C4) ниже порога N недель | `snapshot.ir_v2_month.ir_total` | Н2/Н3/Н4 → МОПу (Н4 → РОПу) |
| **Этап vs 12-мес норма ЗОНЫ** (не месяц!) | `data_division` зоны (coach-биты) | `genCoachTasks` → партнёру по этапу |

> 🔑 **Главный вывод для ПМ:** есть **два «мира норм»**.
> **(1) Месячный план** (`plan.months.norms`) — на нём завязаны сценарии и Н-эскалация (недобор *этого месяца*).
> **(2) 12-месячная норма зоны** (`data_division`) — на ней завязаны только coach-задачи (структурный *навык* на этапе за год).
> Один и тот же этап воронки может дать задачу из разных источников по разной логике.

## 10. Фронт: создание и выполнение

Таб «📋 Задачи и календарь». Список рисует `calendar.js`, **подписываясь напрямую на RTDB**
(`/tasks` по `assignee_code`). Создание из UI: `openCreateTask` → `saveTask` → `__call('createTask', …)`
→ reload. Выполнение: `completeTask`/`skipTask` → `__call('updateTaskStatus', …)`.

> ⚠️ **Важная нестыковка для ПМ:** заявленный инвариант «клиент не пишет `/tasks/` напрямую, только через
> callable» (`tasks.js:2`) **нарушен**: `calendar.js` создаёт/редактирует/завершает/переносит задачи
> **прямыми записями в RTDB**, минуя callable. Значит серверные побочные эффекты (уведомление автору,
> антидубль, проверка прав, автозакрытие по прогрессу) при работе через календарь **не срабатывают**.
> Существуют два несогласованных пути завершения задачи.

## 11. Открытые вопросы / на согласование (для Коли)

1. **Унифицировать типы/статусы:** сид (`skill/manager/open/high`) vs боевые (`client/base/team/free`, `active/…`, `critical/important/normal`).
2. **Единый путь записи задач:** `calendar.js` пишет в RTDB напрямую → терять уведомления/права/антидубль. Либо всё через callable, либо продублировать побочные эффекты.
3. **Сценарии заработают по мере истории:** `no_deals_30d` требует снапшота 30-дневной давности; `ir_dropped_2w` — 14-дневной. На новых данных часть сценариев «молчит», пока не накопится история.
4. **Недельная эскалация:** статус недели считается из `ir_v2_month` на границах 7/14/21/конец мес; отдельного недельного крон-пересчёта стрика нет (TZ-A28 фаза 2).
5. **Два мира норм** (месяц vs зона-12мес) — держать в голове при проектировании новых правил задач.
