## 3. Авторизация — ✅ РАБОТАЕТ (фаза «Фундамент» закрыта)

Вход по коду сотрудника + одноразовый код (OTP) на корпоративный email.
Сессия — Firebase Custom Token, `auth.uid` = код сотрудника.

**Роли:** `realtor` (видит себя) / `mop` (себя + подчинённых) / `rop` (себя +
МОПы и риелторы под ним) / `aup` (видит всех) / `admin` (всех + запись).

`auth-guard.js` уже умеет: `requireAuth()`, `requireAuth({allowedRoles})`,
`getCurrentUser()`, `logout()`, `canRead(user, agentCode, userData)`.
После `requireAuth()` доступен объект `{ code, role, name, seesAll }`.

Cloud Functions (`requestOtp`, `verifyOtp`, `cleanupExpiredOtps`) задеплоены,
работают, письма уходят через SMTP хостинга Hostia. **Их трогать не нужно** —
фаза ЯДРО только про фронтенд и чтение данных.

## 4. Структура Firebase RTDB

### 4.1. `/users/{код}` — пользователи (залито, 3127 записей)

```
/users/{код}/
    name           — ФИО
    email          — корпоративный email
    role           — realtor | mop | rop | aup | admin
    mopCode        — код МОПа (только у realtor; иначе null)
    ropCode        — код РОПа (у realtor и mop; иначе null)
    subordinates   — { кодПодчинённого: true, ... }  (только у mop и rop)
    seesAll        — true только у aup
    createdAt      — timestamp
    lastLoginAt    — timestamp (ставится при входе)
```

### 4.2. `/archive/{YYYY-MM}/{YYYY-MM-DD}/` — ежедневный снимок данных

Архиватор (Google Apps Script, не в этом репозитории) каждую ночь пишет снимок.

```
/archive/{YYYY-MM}/{YYYY-MM-DD}/
    ├── meta/  { agentsCount, date, timestamp, version: "3.0", yearMonth }
    └── agents/{код}/
        ├── name, mop, rop      — ФИО (mop/rop — СТРОКИ-имена, НЕ коды!)
        ├── position            — позиция (число)
        ├── stazh               — стаж в месяцах
        ├── income              — доход
        ├── adCost              — расходы на рекламу
        ├── avgCheck            — средний чек
        ├── prod                — продуктивность (сделок/мес)
        ├── division            — зона светофора (строка): "31-40", "ТОП 1-5",
        │                         "401-500", "без светофора", ...
        ├── comm/               — комиссии (bNew,bSec,bOut,bComm,bGar,sSec,sOut,sComm,sGar)
        ├── b/{сег}/            — покупатель, результирующие за 12 мес
        ├── bL/{сег}/           — покупатель, опережающие (прогнозы)
        ├── s/{сег}/            — продавец, результирующие за 12 мес
        └── sL/{сег}/           — продавец, опережающие
```

**Сегменты:** `all`, `new` (только покупатель), `sec`, `out`, `com`, `gar`.

**Метрики `b/{сег}/` (покупатель, 11):**
`flow` входящий поток · `flowPct` доля сегмента в потоке · `hot` горячие ·
`dep` задатки · `deals` сделки · `mortgage` ипотека · `convHot` конв.поток→горячие ·
`convDep` конв.горячие→задатки · `convFS` конв.поток→сделка · `convHS` конв.горячие→сделка ·
`convDS` конв.задаток→сделка

**Метрики `bL/{сег}/` (покупатель опережающие, 6):**
`flowAct` · `hotAct` · `depCur` · `fcstCur` · `fcstNext` · `closedCur`

**Метрики `s/{сег}/` (продавец, 12):**
`actON` активных объектов в базе · `growON` прирост ОН/мес · `hotPer` горячих ОН ·
`hotCur` горячих текущих · `hotPct` доля горячих · `dep` задатки · `deals` сделки ·
`convHot` · `convDep` · `convDSA` · `convDSH` · `convDSD`

**Метрики `sL/{сег}/` (продавец опережающие, 6):**
`actONCur` · `hotONCur` · `depCur` · `fcstCur` · `fcstNext` · `closedCur`

### 4.3. `/data_division/{зона}/{вид}/{сегмент}/{метрика}` — нормативы

⚠️ **Эта ветка ещё НЕ залита в Firebase.** Нормативы лежат на листе Google-таблицы,
формат не разобран. Это отдельная задача, пока ИР считаем без нормативов (см. ниже).

Когда появится: `{вид}` = `b`|`s`, `{зона}` — нормализованный ключ
(`ТОП 1-5`→`TOP_1-5`, `401-500`→`401-500`, пробелы/точки→`_`), плюс `GOROD`.

### 4.4. Firebase Rules

Уже применены. `/users/{код}` и `/archive/.../agents/{код}` доступны на чтение,
если `auth.uid == код`, либо роль admin/aup, либо код в `subordinates` читающего.
`/otp` и `/rate_limit` закрыты полностью. Менеджер технически может читать
только своих подчинённых — это важно для фазы ЯДРО.

## 5. Формула ИР (Индекс Развития)

```
Общий ИР = ИР_покупателя × 0.5 + ИР_продавца × 0.5

ИР_покупателя = вх_поток × 0.33 + горячие × 0.33 + сделки × 0.34
ИР_продавца   = ОН_в_базе × 0.33 + горячие_ОН × 0.33 + сделки_ОН × 0.34
```

Каждый этап (вх_поток, горячие и т.д.) — это «выполнение» = `факт / норматив`.
Внутри этапа — взвешенная сумма по сегментам, вес сегмента = его доля в потоке
(`b.{сег}.flowPct`).

Метрики:
| Этап покупателя | архив | Этап продавца | архив |
|---|---|---|---|
| вх_поток | `b.{сег}.flow` | ОН_в_базе | `s.{сег}.actON` |
| горячие | `b.{сег}.hot` | горячие_ОН | `s.{сег}.hotPer` |
| сделки | `b.{сег}.deals` | сделки_ОН | `s.{сег}.deals` |

⚠️ Поскольку `/data_division/` ещё не залит — на этом этапе ИР считаем
**в режиме-заглушке**: либо временные хардкод-нормативы в коде (вынести в
отдельный объект-константу, чтобы потом легко заменить на Firebase), либо
ИР как % от плановых значений. Архитектуру кода строить так, чтобы замена
заглушки на реальный `/data_division/` была тривиальной.
